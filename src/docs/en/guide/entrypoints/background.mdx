# Background

Background is the entrypoint for your extension's background logic.
This code runs without its own interface and can respond to browser events even when the popup and other extension pages are closed.
Use Background for startup actions, handling extension installs and updates, subscribing to browser events, and coordinating services.

Create `background.ts` and write the logic you need.
Addon Bone finds the file, creates a background context for the selected browser and manifest version, and registers it in `manifest.json`.
You do not need to register the background manually.

## Quick Start

Start with a console message so you can see when the background starts.
Create `src/background.ts`:

```ts title="src/background.ts"
console.log("Background started");

export {};
```

Build the extension and load it in your browser.
Then open its background console.
In Chrome, go to `chrome://extensions`, enable Developer mode, and click the service worker link on your extension's card.
You will see `Background started` each time the background starts.

Next, log when the extension is installed or updated.
Use `onInstalled` for this.
Replace the contents of the same file:

```ts title="src/background.ts"
import {onInstalled} from "adnbn/browser";

onInstalled((details) => {
    if (details.reason === "install") {
        console.log("Extension installed for the first time");
    }

    if (details.reason === "update") {
        console.log("Extension updated from version", details.previousVersion);
    }
});

export {};
```

When the extension is first installed, you will see the installation message.
When it is updated, you will see a message with the previous version.
Both examples work without additional permissions.

## File Structure

For a single background file, use `background.ts` or `background/index.ts`.
If you have several tasks, split them between `*.background.ts` files or `*.background/` directories with an `index.ts` file.
Addon Bone finds them by name and includes them in the same background context.

<Tabs>
    <Tab label="Default structure">
```tree
src
├── menu.background.ts
└── startup.background/
    └── index.ts
adnbn.config.ts
package.json
```
    </Tab>
    <Tab label="Grouped files">
```tree
src
└── backgrounds/
    ├── menu.background.ts
    └── startup.background/
        └── index.ts
adnbn.config.ts
package.json
```
    </Tab>

Keep files directly in `src` or group them in `backgrounds/`.
The following paths are supported for TypeScript files:

- `background.ts` and `*.background.ts`;
- `background/index.ts` and `*.background/index.ts`;
- `backgrounds/background.ts` and `backgrounds/*.background.ts`;
- `backgrounds/background/index.ts` and `backgrounds/*.background/index.ts`.

:::warning Discovery scope
If Addon Bone finds background entrypoints in `backgrounds/`, it uses only those files for that source scope.
Root-level files in the same scope are not included.
This rule applies separately to app sources and the shared layer, before filtering by browser, app, or manifest version.
:::

Each included file runs its own module code and its own `main`, if defined.
The name `menu.background.ts` helps organize your sources; it does not create a separate background or a callable API named `menu`.

Files are included in this order: plugin entrypoints, the shared layer, then the app.
Within each group, files are sorted lexicographically by path.
This order does not mean that asynchronous work in one `main` finishes before another starts.
If actions depend on each other, run them sequentially in a single startup handler.

<DocHeading level={2} id="definition">Defining Background</DocHeading>

Use `defineBackground` when you need to set options or run actions when the background starts.
The function provides option hints and type checking.
Alternatively, declare options as named exports and export the startup handler through `export default`.

<Tabs>
    <Tab label="Using defineBackground">
```ts title="src/background.ts"
import {defineBackground} from "adnbn";
import {queryTabs} from "adnbn/browser";

export default defineBackground({
    permissions: ["tabs"],
    async main() {
        const tabs = await queryTabs();
        console.log(tabs.map((tab) => tab.title ?? "Untitled tab"));
    },
});
```
    </Tab>
    <Tab label="Named exports">
```ts title="src/background.ts"
import {queryTabs} from "adnbn/browser";

export const permissions = ["tabs"];

export default async () => {
    const tabs = await queryTabs();
    console.log(tabs.map((tab) => tab.title ?? "Untitled tab"));
};
```
    </Tab>
</Tabs>

Both formats support the same options and build filters.
In the named-export format, declare options through `export const`; a function exported through `export default` becomes `main`.
The `primary` badge next to an option marks this mapping.
In this example, `main` gets the open tabs and logs their titles in the background console.
The `tabs` permission allows reading tab titles; Addon Bone adds it to the manifest.

`main` is optional.
The Quick Start runs code at module level, without a separate startup handler.

## Module Code and main

A background file can contain module code and a `main` handler.
Both run each time the background context starts.
You can perform actions and register browser event listeners in either place.

<DocHeading level={3} id="module-code" toc={false}>Module Code</DocHeading>

This code runs when the file loads.
Use it for actions needed as soon as the background loads, such as registering a listener.
Registration creates a subscription; the handler runs when the browser dispatches the event.

<DocHeading level={3} id="main-handler" toc={false}>Actions in main</DocHeading>

Addon Bone calls `main` as the background entrypoint's startup handler.
Use it, for example, to read saved settings or get data through a browser API.
The declaration example uses it to get the titles of open tabs.
You can perform synchronous actions or use `async` / `await`.

`main(options)` receives the options declared in the current file, such as `permissions`.
Options from other background files are not combined into this object.
The handler is optional: if module code and event handlers do all the work, you do not need to define `main`.

You can also register listeners in `main`.
For example, read settings first, then subscribe to events if an extension feature is enabled.
If the subscription is only needed after data is ready, you can `await` that data before registering the listener.
Until registration, this handler does not receive events.

<DocHeading level={3} id="listener-registration" toc={false}>Registering Listeners in Chrome</DocHeading>

For Manifest V3, Chrome recommends registering listeners synchronously at module level when the background script starts.
This lets the browser deliver an event as soon as the service worker starts.
If an event needs to wake the worker and be handled at startup, do not delay registration until asynchronous preparation finishes.
Register the listener immediately and get the data you need inside the handler.
See [Chrome's event registration guidance](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/events).

<DocHeading level={3} id="startup-errors" toc={false}>Startup Errors</DocHeading>

If `main` throws an error or returns a rejected promise, Addon Bone logs the error in the background console.
Other `main` handlers start independently: an error in one does not cancel the others.
The framework does not retry failed operations automatically.

Handle errors inside `main` when you need to recover state or choose another way to perform an action.
Handle event errors inside their callbacks: they run separately from `main`.
Startup error handling does not cover errors in imports or module code.

## Lifecycle

The browser controls when the background starts and stops.
Its behavior depends on the browser and manifest version.

<DocHeading level={3} id="manifest-v3-lifecycle" toc={false}>Manifest V3</DocHeading>

In Chrome and other Chromium browsers, Background runs as a service worker.
The browser can stop an idle worker and start it again when an event needs handling.
On each new start, module code and `main` run again, and in-memory variables are recreated.
A call to `main` does not mean the extension was just installed or the user just opened the browser.

Keep settings and other long-lived data in extension storage.
A new start should restore the state you need rather than repeat one-time actions.
For scheduled tasks, use the Alarms API: a regular `setInterval` stops with the worker and cannot wake it again.
See the [service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) and [Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms).

A service worker has no `window`, `document`, or `localStorage`.

<DocHeading level={3} id="background-pages" toc={false}>Background Pages</DocHeading>

In Manifest V2, Background runs in a background page.
In Firefox, Addon Bone also uses a background page for Manifest V3; the browser can unload it when idle.
A background page has a DOM, but code shared with Chrome Manifest V3 must account for service worker limitations.
See the [background documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background) for differences between environments.

## Manifest Output

Addon Bone bundles the included background files into a single background and registers it in the manifest.

For the Quick Start, the manifest contains these fields:

<Tabs>
    <Tab label="Manifest V3">
```json title="manifest.json"
{
    "manifest_version": 3,
    "background": {
        "service_worker": "js/background.js"
    }
}
```
    </Tab>
    <Tab label="Manifest V2">
```json title="manifest.json"
{
    "manifest_version": 2,
    "background": {
        "scripts": ["js/background.js"]
    }
}
```
    </Tab>
</Tabs>

Only fields related to the example are shown; the full manifest also contains the name, version, and other extension settings.
The path `js/background.js` is illustrative: the actual filename depends on the build mode and may contain a hash.
For Firefox builds with Manifest V3, Addon Bone uses `background.scripts` instead of `background.service_worker`.

Permissions from included entrypoints are combined and deduplicated.
In Manifest V2, `persistent: true` in any included background file applies to the shared background page.
If no file sets this value, the `persistent` field is omitted; Manifest V2 uses a persistent background page by default.
The `persistent` field is omitted in Manifest V3.

## Multi-App Structure

In a project with several apps, put shared background files in `src/shared` and app-specific files in `src/apps/<app>`.
For a single-app project, use the regular `src` directory; you do not need a separate shared layer.

```tree
src
├── shared/
│   └── menu.background.ts
└── apps/
    ├── app-a/
    │   └── startup.background.ts
    └── app-b/
        └── startup.background.ts
adnbn.config.ts
package.json
```

To include shared files and the current app's files in the same background, enable `mergeBackground`:

```ts title="adnbn.config.ts"
import {defineConfig, Workspace} from "adnbn";

export default defineConfig({
    workspace: Workspace.Multi,
    mergeBackground: true,
});
```

`mergeBackground` defaults to `false`:

- With `true`, shared background files and the current app's background files are included together.
- With `false`, if the app has its own background files, the entire app file set replaces the shared set.
- If the app has no background files, the shared set is used.

The app/shared selection happens before entrypoint filters are applied.
If an app file is found but then excluded, for example by `includeBrowser`, shared files are not restored automatically.
Enable `mergeBackground` to run shared and app-specific handlers together.

This combines files, rather than merging their options or handlers into a single definition.
Each file keeps its own options and `main`.

## Best Practices

- **Account for listener registration in Chrome Manifest V3.** For events that need to wake the worker, register listeners synchronously at module level. Get any required data inside the handler.
- **Keep long-lived data outside memory.** When the background stops and starts again, in-memory variables are recreated.
- **Run dependent actions sequentially.** Multiple asynchronous `main` handlers do not form a queue; coordinate dependent operations in one place.
- **Keep permissions close to the code.** If a filter excludes a file, its permissions are excluded from the build too.

## Debugging

1. **The file does not run.** Check its name and location, build filters, and `mergeBackground`. Make sure `backgrounds/` has not changed the discovery scope, and check the `background` field in the final manifest.
2. **Console messages are missing.** Open the background DevTools: in Chrome, the service worker link is on the extension's card at `chrome://extensions` with Developer mode enabled. In Firefox, use the extension debugger at `about:debugging`.
3. **An event is not handled after the worker stops.** In Chrome Manifest V3, check that the listener is registered synchronously when the script starts, before asynchronous preparation. Then trigger the event the code actually subscribes to.
4. **An action repeats unexpectedly.** Check whether a one-time operation is in `main` or module code. Each new background start runs that code again.
5. **State disappears or a timer stops.** Check that required state is saved in storage and that tasks which must survive worker shutdown use the Alarms API.
