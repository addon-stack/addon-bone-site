Background — точка входа для фоновой логики расширения.
Этот код выполняется без собственного интерфейса и может реагировать на события браузера, даже когда popup и другие страницы расширения закрыты.
Используйте Background для действий при запуске, обработки установки и обновлений расширения, подписок на события браузера и координации сервисов.

Создайте `background.ts` и напишите нужную логику.
Addon Bone найдёт файл, создаст фоновый контекст для выбранного браузера и версии манифеста и подключит его в `manifest.json`.
Регистрировать background вручную не нужно.

## Быстрый старт

Начнём с сообщения в консоли, чтобы увидеть, когда запускается background.
Создайте `src/background.ts`:

```ts title="src/background.ts"
console.log("Background started");

export {};
```

Соберите расширение и загрузите его в браузер.
Затем откройте его фоновую консоль.
В Chrome для этого перейдите в `chrome://extensions`, включите режим разработчика и нажмите ссылку на service worker у вашего расширения.
При каждом запуске background вы увидите сообщение `Background started`.

Теперь узнаем, когда расширение установили или обновили.
Для этого используем `onInstalled`.
Замените содержимое того же файла:

```ts title="src/background.ts"
import {onInstalled} from "adnbn/browser";

onInstalled((details) => {
    if (details.reason === "install") {
        console.log("Extension installed for the first time");
    }

    if (details.reason === "update") {
        console.log("Extension updated from version", details.previousVersion);
    }
});

export {};
```

При первой установке расширения вы увидите сообщение об установке.
При обновлении — сообщение с предыдущей версией.
Оба примера работают без дополнительных разрешений.

## Структура файлов

Для одного фонового файла используйте `background.ts` или `background/index.ts`.
Если задач несколько, разделите их между файлами `*.background.ts` или каталогами `*.background/` с файлом `index.ts`.
Addon Bone найдёт их по именам и подключит к одному фоновому контексту.

<Tabs>
    <Tab label="Обычная структура">
```tree
src
├── menu.background.ts
└── startup.background/
    └── index.ts
adnbn.config.ts
package.json
```
    </Tab>
    <Tab label="Группировка файлов">
```tree
src
└── backgrounds/
    ├── menu.background.ts
    └── startup.background/
        └── index.ts
adnbn.config.ts
package.json
```
    </Tab>

Можно хранить файлы непосредственно в `src` или собрать их в папке `backgrounds/`.
Для файлов TypeScript поддерживаются следующие пути:

- `background.ts` и `*.background.ts`;
- `background/index.ts` и `*.background/index.ts`;
- `backgrounds/background.ts` и `backgrounds/*.background.ts`;
- `backgrounds/background/index.ts` и `backgrounds/*.background/index.ts`.

:::warning Область поиска
Если в `backgrounds/` найдены фоновые точки входа, Addon Bone использует только их для этой области исходников.
Файлы на верхнем уровне той же области не добавляются.
Правило применяется отдельно к исходникам приложения и shared-слою, до фильтрации по браузеру, приложению или версии манифеста.
:::

Каждый включённый файл выполняет собственный код и свой `main`, если он объявлен.
Имя `menu.background.ts` помогает организовать исходники; отдельного background или вызываемого API с именем `menu` оно не создаёт.

Файлы подключаются в порядке: точки входа плагинов, shared-слой, затем приложение.
Внутри одного уровня они упорядочиваются лексикографически по пути.
Этот порядок не означает, что асинхронная работа одного `main` завершится до начала другого.
Если действия зависят друг от друга, выполняйте их последовательно в одном обработчике запуска.

## Объявление background

Используйте `defineBackground`, когда нужно задать опции или выполнить действия при запуске фонового кода.
Функция даёт подсказки опций и проверку типов.
Вместо неё можно объявить опции именованными экспортами, а обработчик запуска — через `export default`.

<Tabs>
    <Tab label="Через defineBackground">
```ts title="src/background.ts"
import {defineBackground} from "adnbn";
import {queryTabs} from "adnbn/browser";

export default defineBackground({
    permissions: ["tabs"],
    async main() {
        const tabs = await queryTabs();
        console.log(tabs.map((tab) => tab.title ?? "Untitled tab"));
    },
});
```
    </Tab>
    <Tab label="Именованные экспорты">
```ts title="src/background.ts"
import {queryTabs} from "adnbn/browser";

export const permissions = ["tabs"];

export default async () => {
    const tabs = await queryTabs();
    console.log(tabs.map((tab) => tab.title ?? "Untitled tab"));
};
```
    </Tab>
</Tabs>

Оба формата поддерживают одни и те же опции и фильтры сборки.
В формате с именованными экспортами задавайте опции через `export const`; обычный `export default` соответствует `main`.
Badge `primary` рядом с опцией обозначает именно это соответствие.
В примере `main` получает открытые вкладки и выводит их названия в фоновую консоль.
Разрешение `tabs` позволяет читать названия вкладок; Addon Bone добавит его в манифест.

`main` необязателен.
В Quick Start код выполняется на уровне модуля, без отдельного обработчика запуска.

## Код модуля и main

В фоновом файле можно писать код на уровне модуля и объявлять `main`.
Оба выполняются при каждом новом запуске background.
В обоих местах можно выполнять действия и регистрировать слушателей браузерных событий.

<DocHeading level={3} id="module-code" toc={false}>Код на уровне модуля</DocHeading>

Этот код выполняется при загрузке файла.
Используйте его для действий, которые нужны сразу при загрузке background, например для регистрации слушателя.
Регистрация создаёт подписку; сам обработчик выполняется, когда браузер отправляет событие.

<DocHeading level={3} id="main-handler" toc={false}>Действия в main</DocHeading>

Addon Bone вызывает `main` как обработчик запуска фоновой точки входа.
Используйте его, например, чтобы прочитать сохранённые настройки или получить данные через браузерный API.
В примере объявления background это получение названий открытых вкладок.
Можно выполнять синхронные действия или использовать `async` / `await`.

`main(options)` получает опции, объявленные в текущем файле, например `permissions`.
Опции других background-файлов в этот объект не объединяются.
Сам `main` необязателен: если вся работа выполняется на уровне модуля и в обработчиках событий, объявлять его не нужно.

В `main` тоже можно регистрировать слушателей.
Например, сначала прочитать настройки, а затем подписаться на события, если функция расширения включена.
Если подписка нужна только после подготовки данных, можно дождаться их через `await`, а затем зарегистрировать слушателя.
До регистрации этот обработчик ещё не принимает события.

<DocHeading level={3} id="listener-registration" toc={false}>Регистрация слушателей в Chrome</DocHeading>

Для Manifest V3 Chrome рекомендует регистрировать слушателей синхронно на уровне модуля при запуске фонового скрипта.
Это позволяет браузеру передать событие сразу после запуска service worker.
Если событие должно пробуждать worker и обрабатываться при его запуске, не откладывайте подписку до окончания асинхронной подготовки.
Зарегистрируйте слушателя сразу, а нужные данные получите внутри обработчика.
Подробнее — [рекомендации Chrome по регистрации событий](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/events).

<DocHeading level={3} id="startup-errors" toc={false}>Ошибки при запуске</DocHeading>

Если `main` выбросит ошибку или вернёт отклонённый promise, Addon Bone запишет ошибку в консоль фонового контекста.
Остальные обработчики `main` запускаются независимо: ошибка одного не отменяет остальные.
Фреймворк не повторяет неудавшуюся операцию автоматически.

Обрабатывайте ошибки внутри `main`, когда нужно восстановить состояние или выбрать другой способ выполнить действие.
Ошибки обработчиков событий обрабатывайте внутри этих обработчиков: они выполняются отдельно от `main`.
Эта обработка ошибок запуска не защищает от ошибок в импортах или коде на уровне модуля.

## Жизненный цикл

Браузер управляет запуском и остановкой background.
Его поведение зависит от браузера и версии манифеста.

<DocHeading level={3} id="manifest-v3-lifecycle" toc={false}>Manifest V3</DocHeading>

В Chrome и других браузерах Chromium Background работает как service worker.
Браузер может остановить неактивный worker и запустить его снова, когда потребуется обработать событие.
При новом запуске код модуля и `main` выполняются заново, а переменные в памяти создаются заново.
Запуск `main` не означает, что расширение только что установили или что пользователь только что открыл браузер.

Храните настройки и другие долговременные данные в хранилище расширения.
Повторный запуск должен восстанавливать нужное состояние, а не повторять одноразовые действия.
Для задач по расписанию используйте Alarms API: обычный `setInterval` прекращает работу вместе с worker и не может запустить его снова.
Подробнее — [жизненный цикл service worker](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) и [Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms).

В service worker нет `window`, `document` и `localStorage`.

<DocHeading level={3} id="background-pages" toc={false}>Фоновые страницы</DocHeading>

В Manifest V2 Background выполняется в фоновой странице.
В Firefox Addon Bone также использует фоновую страницу для Manifest V3; браузер может выгружать её при бездействии.
У фоновой страницы есть DOM, но код, общий с Chrome Manifest V3, должен учитывать ограничения service worker.
Различия сред описаны в [документации по background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

## Результат сборки

Addon Bone собирает включённые фоновые файлы в общий background и указывает его в манифесте.

Для Quick Start манифест будет содержать следующие поля:

<Tabs>
    <Tab label="Manifest V3">
```json title="manifest.json"
{
    "manifest_version": 3,
    "background": {
        "service_worker": "js/background.js"
    }
}
```
    </Tab>
    <Tab label="Manifest V2">
```json title="manifest.json"
{
    "manifest_version": 2,
    "background": {
        "scripts": ["js/background.js"]
    }
}
```
    </Tab>
</Tabs>

Показаны только поля, связанные с примером; полный манифест также содержит название, версию и остальные настройки расширения.
Для наглядности показан путь `js/background.js`: фактическое имя файла зависит от режима сборки и может содержать хеш.
В сборке Firefox с Manifest V3 Addon Bone использует `background.scripts` вместо `background.service_worker`.

Разрешения включённых точек входа объединяются и очищаются от повторов.
В Manifest V2 значение `persistent: true` хотя бы в одном включённом фоновом файле применяется к общей фоновой странице.
Если такого значения нет, поле `persistent` не добавляется; в Manifest V2 браузер использует постоянную фоновую страницу по умолчанию.
В Manifest V3 поле `persistent` не добавляется.

## Multi-App Structure

В проекте с несколькими приложениями поместите общие фоновые файлы в `src/shared`, а файлы конкретного приложения — в `src/apps/<app>`.
В single-app проекте используйте обычный `src`; отдельный shared-слой не требуется.

```tree
src
├── shared/
│   └── menu.background.ts
└── apps/
    ├── app-a/
    │   └── startup.background.ts
    └── app-b/
        └── startup.background.ts
adnbn.config.ts
package.json
```

Чтобы подключить к одному background общие файлы и файлы текущего приложения, включите `mergeBackground`:

```ts title="adnbn.config.ts"
import {defineConfig, Workspace} from "adnbn";

export default defineConfig({
    workspace: Workspace.Multi,
    mergeBackground: true,
});
```

`mergeBackground` по умолчанию равен `false`:

- При `true` в сборку входят фоновые файлы shared-слоя и текущего приложения.
- При `false`, если в приложении обнаружены свои фоновые файлы, весь набор файлов приложения используется вместо shared-набора.
- Если фоновых файлов приложения нет, используется shared-набор.

Выбор app/shared происходит до применения фильтров точки входа.
Если файл приложения найден, но затем исключён, например по `includeBrowser`, shared-файлы автоматически не возвращаются.
Для совместного выполнения общих и локальных обработчиков включите `mergeBackground`.

Это объединение файлов, а не опций или обработчиков в одно определение.
Каждый файл сохраняет собственные опции и `main`.

## Практические рекомендации

- **Учитывайте регистрацию слушателей в Chrome Manifest V3.** Для событий, которые должны пробуждать worker, регистрируйте подписки синхронно на уровне модуля. Нужные данные можно получить внутри обработчика.
- **Храните долговременные данные вне памяти.** После остановки и повторного запуска фонового контекста переменные создаются заново.
- **Выполняйте связанные действия последовательно.** Несколько асинхронных `main` не образуют очередь; координируйте зависимые операции в одном месте.
- **Держите разрешения рядом с кодом.** Если файл исключён фильтром, его разрешения тоже не попадут в сборку.

## Отладка

1. **Файл не выполняется.** Проверьте имя и расположение файла, фильтры сборки и `mergeBackground`. Убедитесь, что папка `backgrounds/` не переключила область поиска, и проверьте поле `background` в итоговом манифесте.
2. **Не видно сообщений в консоли.** Откройте DevTools фонового контекста: в Chrome ссылка на service worker находится на карточке расширения в `chrome://extensions` при включённом режиме разработчика. В Firefox используйте отладчик расширения в `about:debugging`.
3. **Событие не обрабатывается после остановки worker.** В Chrome Manifest V3 проверьте, что слушатель регистрируется синхронно при запуске скрипта, до асинхронной подготовки. Затем вызовите именно то событие, на которое подписан код.
4. **Действие повторяется неожиданно.** Проверьте, не находится ли одноразовая операция в `main` или коде на уровне модуля. Новый запуск фонового контекста снова выполнит этот код.
5. **Исчезает состояние или завершается таймер.** Проверьте, хранится ли нужное состояние в хранилище и используется ли Alarms API для задач, которые должны переживать остановку worker.
