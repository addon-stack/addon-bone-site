`background` is the backend entrypoint of your browser extension in Addon Bone.
It runs in the background without a visible UI and acts as the central hub of your extension.
Addon Bone automatically generates the background service worker (MV3) or background page (MV2) from your source files — you just write the logic, and the framework handles manifest configuration, file merging, and build output.

Use `background` for startup logic, browser event listeners, command handling, messaging orchestration, and privileged extension APIs.

## Quick Start

Create `background.ts` and write your first extension logic directly at the top level.

This is the quickest way to get started with Addon Bone background: no boilerplate, no extra setup, just a real background module that starts doing useful work immediately.

```ts title="src/background.ts"
console.log("Background started");

export {};
```

<EntrypointExportNote/>

Here is a more practical example — listening for the extension install event using [browser API wrappers](/guide/extension-apis):

```ts title="src/background.ts"
import {onInstalled} from "adnbn/browser";

onInstalled((details) => {
    if (details.reason === "install") {
        console.log("Extension installed for the first time");
    }

    if (details.reason === "update") {
        console.log("Extension updated from version", details.previousVersion);
    }
});

export {};
```

## File Structure

Addon Bone auto-discovers background entrypoints by file naming patterns — no manual registration or manifest editing is required.
Use the default flat structure for most projects. If you have many background files, group them in `backgrounds/` to separate concerns and organize logic by feature.

Supported patterns include:

- `background.ts`
- `*.background.ts`
- `background/index.ts`
- `*.background/index.ts`
- `backgrounds/background.ts`
- `backgrounds/*.background.ts`
- `backgrounds/background/index.ts`
- `backgrounds/*.background/index.ts`

:::warning Scope rule
If a `backgrounds/` directory contains background entrypoints, Addon Bone scans only that directory for background entrypoints in the same scope and does not merge them with root-level background files.
:::

During build, Addon Bone merges all discovered background entrypoints into a single service worker (MV3) or background script (MV2).
You can split logic into multiple files, and the framework will combine them automatically.

Merge order:

1. **External entrypoints** — provided by plugins.
2. **Shared entrypoints** — from the configured shared layer (in multi-app mode).
3. **App-specific entrypoints** — from the current app directory.

Within the same priority level, files are sorted by lexicographic path comparison.

:::info
Options are not merged between files into a single object. Each file is processed independently.
Only aggregate manifest fields (such as `permissions`) are combined in the final output.
:::

## Definition

`main` is a framework-provided execution function for the `background` entrypoint — it is not part of the browser API, but a convention introduced by Addon Bone. It is not required.
You can define only options (for example `permissions`) and keep top-level logic without declaring `main`.

Use `main` when you want a dedicated entry function for background startup logic.
It can be both sync and async — no additional `try-catch` wrapping is needed.
Addon Bone invokes `main` in a protected execution flow and logs runtime errors, so one failing handler does not break the entire background startup pipeline.

## Options

Options are declarative settings recognized by Addon Bone at build time.
They control how the entrypoint is included in the build and what fields are added to `manifest.json` — you never need to edit the manifest manually.
For manifest-related fields, Addon Bone aggregates compatible values across discovered background entrypoints and deduplicates repeated items in the final manifest output.

## Multi-App Structure

Use this structure when one project builds several extension apps from the same codebase.

Shared background logic lives in `src/shared`.
Use it for code that every app needs, such as install/update handlers, shared browser events, API clients, or common permissions.

App-specific background logic lives in `src/apps/<app>`.
Use it for behavior that belongs only to one app, such as product-specific events, permissions, integrations, or startup logic.

In a single-app project, you do not need this structure.
Addon Bone works with your normal `src` files directly.

```tree file="./code/background.multi-app.tree"
```

Background naming patterns work the same way in both layers: `src/shared` and `src/apps/<app>`.
The app files can add background behavior that only one app needs; they do not need to repeat the shared filenames.

<DocHeading level={3} id="multi-app-configuration" toc={false}>Configuration</DocHeading>

```ts title="adnbn.config.ts"
import {defineConfig, Workspace} from "adnbn";

export default defineConfig({
  workspace: Workspace.Multi,

  // Merges shared background and app background
  mergeBackground: true,
});
```

<DocHeading level={3} id="multi-app-merge" toc={false}><code>mergeBackground</code> behavior</DocHeading>

`workspace: Workspace.Multi` enables the shared/app source layout.
`mergeBackground` controls what happens when the shared layer and the current app both provide background entrypoints.

- `mergeBackground: true`  
  Shared and app background entrypoints are included together.
- `mergeBackground: false`  
  App background entrypoints replace shared background entrypoints when the app has its own files.  
  If the app has no background entrypoints, shared background entrypoints are used as a fallback.

This lets you keep a shared background baseline and add app-specific behavior only where an app needs it.

## Best Practices

<DocHeading level={3} id="best-practices-critical" toc={false}>Critical</DocHeading>

- **Use one structure style per scope: root-level or `backgrounds/`.**  
  If `backgrounds/` contains background entrypoints in a scope, only that directory is used, and root-level background files in the same scope are ignored.

- **Each entrypoint should be self-sufficient for critical fields.**  
  Declare critical fields (`permissions`, `hostPermissions`, optional permissions) in each entrypoint that needs them.  
  Entrypoints can be excluded by developer-defined build filters (for example `excludeApp`, `excludeBrowser`, `includeApp`, `includeBrowser`), so relying on another file to "provide" those fields can break the final manifest.

- **Account for build filters** (`includeBrowser`, `excludeBrowser`, `includeApp`, `excludeApp`, `mode`, `debug`, `manifestVersion`).  
  If an entrypoint can be excluded, critical options should also be declared in fallback entrypoints.

<DocHeading level={3} id="best-practices-recommended" toc={false}>Recommended</DocHeading>

- Keep options close to the background logic that uses them.  
  If a module relies on `tabs`, `storage`, or host access, declare the corresponding options in the same entrypoint.

- In multi-app mode, treat `shared` as the baseline and `apps/*` as app-specific layers.  
  Keep shared logic in `shared`, and put differences/overrides in each app.

- Prefer [`defineBackground`](#definition) as the default style for new modules.  
  It provides stronger TypeScript typing, better autocomplete, and fewer option-related mistakes.

## Debugging

To inspect and debug the background entrypoint:

1. Open `chrome://extensions` (or the equivalent in your browser).
2. Make sure **Developer mode** is enabled.
3. Find your extension and click **Inspect views → service worker** (MV3) or **Inspect views → background page** (MV2).
4. This opens a dedicated DevTools window where you can see console output, set breakpoints, and inspect network requests from the background context.

:::tip
If the service worker is inactive, triggering any registered event (for example, clicking the extension icon) will restart it and attach the debugger.
:::
