`background` is the backend entrypoint of your browser extension in Addon Bone.

In browser terms, this entrypoint maps to:

- **Manifest V3**: background **service worker**
- **Manifest V2**: background **page** (persistent or non-persistent)

Use background for startup logic, browser event listeners, command handling, messaging orchestration, and privileged extension APIs.

## Quick Start

Create `background.ts` and write your first extension logic directly at the top level.

This is the fastest way to feel how Addon Bone background works: no boilerplate, no extra setup, just a real background module that starts doing useful work immediately.

```ts title="background.ts"
console.log("Background started");

export {};
```

## File Structure

Addon Bone auto-discovers background entrypoints by file naming patterns.
Use the default flat structure for most projects. If you have many background files, group them in `backgrounds/`.

    <Tab label="Grouped">

    </Tab>

Supported patterns include:

- `background.ts`
- `*.background.ts`
- `background/index.ts`
- `*.background/index.ts`
- `backgrounds/background.ts`
- `backgrounds/*.background.ts`
- `backgrounds/background/index.ts`
- `backgrounds/*.background/index.ts`

Scope rule: if a `backgrounds/` directory exists, Addon Bone scans only that directory for background entrypoints in the same scope and does not merge it with root-level background files.

All discovered background entrypoints are merged into one final background output during build.
You can split logic into multiple files, and Addon Bone will combine them automatically.


## Definition

`main` is the target handler for the `background` entrypoint, but it is not required.
You can define only options (for example `permissions`) and keep top-level logic without declaring `main`.

Use `main` when you want a dedicated async-safe execution point for background startup logic.

Background can be declared in two formats:

- **Recommended (`defineBackground`)**: the default choice for getting started and for day-to-day development.
  `defineBackground` provides strict TypeScript declarations: autocomplete, full option hints, and inline type validation while you write. This helps you avoid mistakes and understand the framework API faster.
- **Advanced (explicit exports)**: for cases where you already know the available fields and their types.
  Options are declared via named exports, and the target handler is declared via `export default`. This style is useful when you want a more manual and fast setup without importing a helper.

## Options

Options are declarative settings for an entrypoint file.
They define:

- which entrypoints are included in the build and which are excluded;
- which fields are added to `manifest.json`.

For `background`, this includes fields such as `permissions`, `optionalPermissions`, `hostPermissions`, `persistent`, and others.

## Multi-App Structure

Use this mode when you build multiple extensions from a single codebase.

Typical scenario:
- you have shared logic (core modules, API layer, part of background logic);
- and per-app differences (design, feature set, audience, integrations).

With Addon Bone, you can keep shared logic in one place and extend it per app.

```tree file="./code/background.multi-app.tree"
```

Background naming patterns in multi-app mode are the same as in the default structure:
- `background.ts`
- `*.background.ts`
- `background/index.ts`
- `*.background/index.ts`
- grouped structure via `backgrounds/`

This works the same way:
- inside `shared`;
- inside each app under `apps/*`.

<DocHeading level={3} id="multi-app-configuration" toc={false}>Configuration</DocHeading>

```ts title="adnbn.config.ts"
import {defineConfig} from "adnbn";

export default defineConfig({
  // Enables shared mode:
  // true -> uses "shared" directory by default
  // false -> shared mode is disabled
  // string -> custom directory name for shared layer
  shared: true,

  // Merges shared background and app background
  mergeBackground: true,

  // Optional: apps directory can also be renamed
  // apps: "applications",
});
```

<DocHeading level={3} id="multi-app-merge" toc={false}><code>mergeBackground</code> behavior</DocHeading>

- `mergeBackground: true`  
  Shared and app backgrounds are merged.
- `mergeBackground: false`  
  If an app background exists, only app background is used.
- If an app background does not exist  
  Shared background is used.

This lets you keep one shared baseline and add app-specific behavior without duplicating the full structure.

## Best Practices

1. Keep each background file self-sufficient: logic and required manifest-affecting options together.
2. Declare required permissions/optional permissions/host permissions in each file that depends on them.
3. Do not rely on another background file to provide required options.
4. This is critical when filters (`includeBrowser`, `excludeApp`, `mode`, `debug`, `manifestVersion`) may exclude files from build output.
